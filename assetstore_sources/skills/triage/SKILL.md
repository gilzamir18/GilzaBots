# Triage

Move issues on the project's issue tracker through a small state machine of triage roles.

How to reach the tracker, and whether external pull requests are a request surface, is in `docs/agents/issue-tracker.md`; the label strings are in `docs/agents/triage-labels.md`. Both are written by `/setup-engineering-skills`: if they don't exist, tell the user to run it first. Tracker operations go through its CLI with `run_command` (`gh`, `glab`), or, on a local tracker, through the ticket files under `.scratch/`.

When PRs are in scope, triage covers them too: **a PR is an issue with attached code**, with the same roles, the same states and the same machine, plus the deltas marked "for a PR" below. Resolve a bare `#42` to an issue or a PR the way the tracker doc says.

Every comment or issue you post during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

In this skill's directory; read them with `read_file` when the step needs them:

## Roles

Two **category** roles:

- `bug`: something is broken;
- `enhancement`: a new feature or an improvement.

Five **state** roles:

- `needs-triage`: the maintainer needs to evaluate it;
- `needs-info`: waiting on the reporter for more information;
- `ready-for-agent`: fully specified, ready for an AFK agent;
- `ready-for-human`: needs a human to implement it;
- `wontfix`: will not be actioned.

For a PR, the states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it is ready for a human to merge.

Every triaged item carries exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before anything else.

These are canonical role names; the label strings in the tracker may differ, and `triage-labels.md` maps them.

Transitions: an unlabelled item normally goes to `needs-triage` first; from there to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer runs `/triage` and says what they want in plain language. Interpret it and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the tracker and present three buckets, oldest first:

1. **Unlabelled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

When PRs are in scope, include external PRs and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker doc defines who counts as external), so a collaborator's in-flight PR is not triage work. That filter is for discovery only: a PR the maintainer names is always triaged.

Show the counts and one line per item, and let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the whole item (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase with the vocabulary of `GLOSSARY.md`, respecting the ADRs in the area. Run two checks: (a) **redundancy**: search for an existing implementation of the requested behaviour by domain concept, not just the request's wording, and report where you looked; if found, it is an already-implemented `wontfix` (step 5); (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Give the maintainer your category and state recommendation with the reasoning, plus a brief summary of the relevant code (including whether it is already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out and run the relevant tests or commands. Report what happened: confirmed (with the code path), failed, or not enough detail (a strong `needs-info` signal). A confirmed verification makes a much stronger brief.

4. **Grill, if needed.** If the request needs fleshing out, load `grilling` and `domain-modeling` and grill it into shape one round at a time, sharpening domain terms and updating `GLOSSARY.md` and ADRs inline as decisions land.

5. **Apply the outcome** (show the maintainer what you will post before posting it):
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: the same structure as an agent brief, plus why it can't be delegated (judgement calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - `wontfix`: close the item, with a comment that depends on *why*:
     - **Already implemented**: point to where it lives. Do **not** write to `.out-of-scope/`: that knowledge base is for *rejected* requests, not built ones.
     - **Rejected (bug)**: a polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role, with a comment if there is partial progress.

## Quick state override

When the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you are about to do (role changes, comment, close), then act. Skip grilling. When moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Put everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, never "please provide more info".

## Resuming a previous session

If prior triage notes exist on the item, read them, check whether the reporter answered the outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
